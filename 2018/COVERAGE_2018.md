# BARR-C:2018 Enforcement Coverage Map

Which of the 167 rules of BARR-C:2018 this kit enforces automatically, by which mechanism, and which rules remain code-review territory. Generated by gen_coverage.py from the 2018 rule inventory and the kit's actual configuration files; the mappings are exercised by `tests/run_tests.sh`.

Rule snippets below are abridged locators. The full rule text and its reasoning live in the book, which is free: <https://barrgroup.com/embedded-c-coding-standard>.

## Summary

| Coverage | Rules | Meaning |
|---|---|---|
| Gated | 53 | At least one kit mechanism fails the build on violation |
| Advisory | 2 | Reported by check.sh but never fails the build (preferred-practice rules) |
| Automatable, not in kit | 12 | The 2018 analysis classed these as tool-checkable; the kit does not yet gate them |
| Code review only | 100 | Human judgment (comments, design intent, naming quality, hardware knowledge) |

A rule counted as Gated is not necessarily *fully* enforced; partial-scope mechanisms carry a note in the table. The honest reading is: the gate catches the mechanical core of the rule, review still owns the judgment at its edges.

## Rules covered by two or more mechanisms

The question multi-tool coverage raises: can two mechanisms disagree, one passing what the other fails? And is any pair truly contradictory, tool A demanding what tool B forbids?

| Rule | Mechanisms | Can they disagree? | Contradictory? |
|---|---|---|---|
| 8.3.b | bugprone-switch-missing-default-case + -Wswitch-default | Yes: the clang-tidy check deliberately skips enum-typed switch conditions, while the compiler flag fires on every switch. An enum switch without a default fails the compiler and passes clang-tidy. | No. The mechanisms disagree only in the union direction; adding the default block the rule requires satisfies both. |
| 8.2.c | bugprone-assignment-in-if-condition + -Werror=parentheses | Yes: an extra parenthesis pair, if ((x = y)), suppresses the compiler diagnostic by design but still fails clang-tidy. | No. clang-tidy is the stricter superset, which matches the rule: BARR-C forbids the assignment outright, parenthesized or not. |
| 7.2.a | cppcoreguidelines-init-variables + -Wuninitialized | Yes: declare-then-assign-then-use passes the compiler's flow analysis but fails clang-tidy, which wants an initializer at the declaration. | No. Union direction again; initializing at declaration satisfies both. |
| 6.2.f | misc-unused-parameters + -Wunused-parameter | Both fire on the same defect in the same direction. | No. Remediation for a deliberately unused parameter is a (void) cast, which satisfies both (removing the parameter name is not valid C before C23). |
| 6.1.c / 7.1.c | bugprone-reserved-identifier + readability-identifier-naming | Both can fire on the same leading-underscore name, in the same direction. | No. Two findings for one defect, one fix. |
| 1.2.a and the white-space family | .clang-format (gated) + .editorconfig (editor-only) | Edge case: a single unbreakable token longer than 80 columns passes clang-format (which cannot break it) while an editorconfig-aware editor still flags it. | No. The values are identical; .editorconfig is advisory tooling for editors and never a CI gate. clang-format is the authority. |
| 8.3.c | -Wimplicit-fallthrough under gcc vs clang | Yes, on conformant code: gcc honors the fall-through comment that Rule 8.3.c itself prescribes; clang ignores comments and requires __attribute__((fallthrough)). A compliant commented fall-through passes gcc and fails clang with -Werror. | This is the closest thing to a contradiction in the kit, and it is between two compilers, not two kit mechanisms. Resolution: the flag is specified with gcc semantics; clang users add the attribute alongside the comment. The validation suite pins gcc for this fixture. |

**Verdict: there is no contradictory pair.** No kit mechanism demands what another forbids. Every overlap is a union: the stricter mechanism subsumes the looser one, and one compliant fix satisfies all of them. Structurally this holds because clang-format never rewrites identifiers and never inserts or removes braces, so the formatter cannot manufacture a clang-tidy violation. The standing empirical proof is the format round-trip test in `tests/run_tests.sh`: format a file in place, then every other gate must still pass.
